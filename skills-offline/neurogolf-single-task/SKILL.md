# NeuroGolf Single-Task Optimizer

## Goal

Work exactly one user-named task toward one user-given target score. If the
user did not give a numeric target, ask for one before starting task work.

The work ends only when a candidate **evaluates to `status=ok`** (correct on
the bundled known examples; optionally also clean on extra fresh samples for
robustness) **and its score reaches the target**. Do not stop short of that.

Derive the budget immediately from the metric:

```text
score = 25 - ln(memory_bytes + params)
=>  m + p <= exp(25 - target)
```

Every design decision is judged against that budget. The candidate does not
need to be a readable implementation of the rule: the graph may be unreadable
if it satisfies the evaluator contract and improves the metric.

## Trust Doctrine

Solve the task from your own understanding of how it should be solved. Prior
recorded conclusions — wherever they appear — are treated as unverified
hypotheses, never as facts.

Trusted ground truth:

- The task JSON examples (bundled under the `evaluate` skill).
- ARC-GEN, ARC-DSL, and Code Golf 2025 reference sources (`reference`).
- The `metric` skill contract.
- Your own local measurements (`inspect-onnx`, `evaluate`).

Assumed wrong until re-derived: every "failed", "infeasible", or "dead end"
note in any bundled trick doc or prior artifact. Such a note means **"not
solved yet"** — often a lazy stop, under-exploration, a too-weak feature basis,
or a missed trick. No idea may be dismissed because a prior agent gave up on
it. Re-derive every claim with your own reasoning and measurements before
accepting it.

## The Bar

The starting bar is the current baseline ONNX for the task. The baseline is generated by
`solutions_py/taskNNN.py`, a dense Python builder of the current champion in this bundle's
`solutions_py/`. Run it to materialize `taskNNN.onnx`, then measure its score, memory, and params
with `evaluate`/`inspect-onnx` and record that as the bar. Beating the bar is good progress, but the
**target**, not the bar, decides when the work is done.

## Floor Arithmetic

Before investing in any topology — including a candidate of your own — compute
its floor: the minimum `m + p` the family can reach after every conceivable
trim. Re-derive the floor whenever the design changes.

- **Floor > budget** means the family cannot be the *finishing* route — trims
  cannot bridge a topology gap, so do not grind it toward the target. If its
  floor still beats the current bar's `m + p`, it is worth building as an
  intermediate best; bank it, then return to target-route hunting.
- **Floor <= budget** makes the family a target-route candidate; these get the
  deep investment.

If solver-proven infeasibility accumulates at the budget across increasingly
general families, the target itself may sit above the task's reachable ceiling.
That is a finding, not a stop: report to the user the best proven-feasible
total, the best achieved score, and the infeasibility evidence, and ask whether
to revise the target. Never silently stall and never lower the target on your
own judgment.

## Task Start

Set `SKILLS_DIR` to the root of this unzipped bundle (the parent of this skill
folder), then:

1. Read the cached task pattern with `neurogolf-task-semantics`. If missing,
   create it from ARC-GEN, ARC-DSL, and Code Golf 2025 and validate it.
2. Run `reference_lookup.py` and read the reference solver, generator, and Code
   Golf sources. The generator matters doubly here: it defines the restricted
   input manifold the candidate actually has to be correct on.
3. Measure the baseline ONNX (materialize it by running `solutions_py/taskNNN.py`) to record the
   bar — score, memory, params — and compute the target budget.

```bash
TASK=taskNNN
OUT=/tmp/neurogolf_single_task/$TASK
SKILLS_DIR=/path/to/unzipped/skills-offline
SEMANTICS_SKILL_DIR="$SKILLS_DIR/neurogolf-task-semantics"
REFERENCE_SKILL_DIR="$SKILLS_DIR/reference"
INSPECT_ONNX_SKILL_DIR="$SKILLS_DIR/inspect-onnx"
EVALUATE_SKILL_DIR="$SKILLS_DIR/evaluate"
SOLVER_SKILL_DIR="$SKILLS_DIR/solver-search"

mkdir -p "$OUT"
python "$SEMANTICS_SKILL_DIR/scripts/task_semantics.py" status "$TASK"
python "$SEMANTICS_SKILL_DIR/scripts/task_semantics.py" show "$TASK"
# If the cache is missing, run:
python "$SEMANTICS_SKILL_DIR/scripts/task_semantics.py" init "$TASK"
python "$REFERENCE_SKILL_DIR/scripts/reference_lookup.py" "$TASK"

# Record the bar from the current baseline (run the dense champion builder to materialize it).
python "$SKILLS_DIR/solutions_py/$TASK.py" "$OUT/$TASK.onnx"
python "$EVALUATE_SKILL_DIR/scripts/evaluate.py" --input "$OUT/$TASK.onnx" --tasks "$TASK" --verbose
python "$INSPECT_ONNX_SKILL_DIR/inspect_onnx.py" "$OUT/$TASK.onnx" --task-id "$TASK" --include-inits
```

After `init`, fill every TODO in the semantic cache by reading the listed
reference files, then run `validate` before designing. Design blind from the
semantics first; treat the baseline graph as prior work, not a blueprint.

## Design Phase (Blind)

1. State precisely what each output cell depends on: global features (color
   counts, grid size), local neighborhood, coordinates, object attributes, or
   another bounded feature vector. Write this dependence down before touching
   ONNX.
2. **Exploit the sign rule, not exact logits.** Match the scorer's sign rule,
   not argmax: the contract is only `correct channel > 0` and
   `wrong channels <= 0`, with padded cells non-positive/zero-hot. Do not
   reproduce the baseline's values or any reference's exact outputs — any
   separator that gets the signs right is correct.
3. **Exploit the restricted generator manifold.** Candidates only need to be
   correct on inputs the ARC-GEN generator can actually produce, not on
   arbitrary tensors. Several wins come from solving a much smaller sign table
   over generator-reachable feature combinations than a general all-input
   function would require. Read the generator constraints carefully and shrink
   the table before searching.
4. Extract a finite behavior table from **your own validated reference
   implementation** — the semantic cache `solve(grid)` or the ARC-DSL solver —
   over generator-reachable inputs, with per-cell rows like
   `global features + local features -> expected positive output channel`.
   Do not extract from the baseline graph. Write task-specific extraction
   tooling under `/tmp`.
5. Design the minimal computation implementing the rule, ideally a compact
   direct-output family: finite tables, low-dimensional color bases,
   low-rank/CP/Tucker factorizations, compact route encodings, threshold
   predicates, output-only contractions (e.g., one-node `Einsum`).
6. **Use the math toolbox.** Derive the representation mathematically first,
   then let search find the constants: low-rank matrix/tensor factorization
   (SVD, CP/Tucker), linear separability and LP duality for sign tables,
   polynomial/Lagrange interpolation over small finite domains, Vandermonde
   systems, modular arithmetic and CRT for periodic or index-routing rules,
   finite differences for cumulative/positional patterns, trigonometric or
   exponential identities for compact periodic constants, and
   convexity/threshold arguments to prove a separator exists before searching
   for it.
7. Prove feasibility with an intentionally oversized direct-output family
   first. The oversized artifact is evidence that the feature basis works, not
   the final target — compress it afterwards.
8. `solver-search` is a first-class route: LP/HiGHS for fixed-feature
   coefficient feasibility, Z3 for exact bounded formulas and equivalence,
   CP-SAT for discrete constants and operator choices, brute force for small
   bounded spaces — synthesized directly from the semantics, not from the
   baseline's structure.
9. **Keep a hypothesis ledger.** Record every representation family tried in
   `$OUT/notes.md` with its exact kill scope: "polynomial separators
   infeasible through degree 8 over the full generator", "trig gate-products
   infeasible through period 41". A killed family is a map edge, not a failure.
   Each new lane must be materially different from every ledger entry; never
   silently retry a killed scope.
10. **Verify over the full generator state space.** When the finite state space
    is enumerable, validate candidates against ALL of it, not just the bundled
    examples — exact-on-examples is routinely overfit and dies on the
    exhaustive check. Record the state-space size and the zero-wrong count.
11. Keep the dense `[1,10,30,30]` tensor as the graph output; the evaluator
    excludes graph input and output boundary tensors from activation memory.
12. PyTorch/NumPy scratch prototypes are allowed as design evidence, and
    offline training of compact constants is a valid design route. Training is
    experiment work only: submitted builders stay deterministic, never train or
    read checkpoint files at runtime, and serialize trained constants as
    ordinary dense numeric initializers built in code.
13. Use `evaluate-gpu` for fast local correctness checks during iteration. It
    is CUDA-only with no CPU fallback; high-arity Einsum graphs that take
    minutes on CPU often run in seconds on GPU.
14. Build v1 even if it does not beat the bar, then iterate from your own
    design. Keep each candidate that beats the bar as the new best, then keep
    going. The first attempt is a starting point, not a verdict; the target —
    not the next small win — ends the work.

Candidates may use any valid ONNX operators unless another active user
instruction narrows the lane. Builders must be deterministic, self-contained,
and readable as construction code: **never produce Python builders containing
base64 blobs** (or other encoded-bytes payloads) — serialize constants as
ordinary dense numeric initializers built in code. No sparse tensors. Do not
read reference files or the semantic cache from builders.

## Idea Inventory

Only after you have your own candidate, use the baseline ONNX (`inspect-onnx`)
and the bundled trick docs at the bundle root as an **idea inventory**, never as
a verdict source:

```text
$SKILLS_DIR/ALL_OPERATORS_ONNX_DOC.md
$SKILLS_DIR/TECHNIQUES.md
$SKILLS_DIR/OPTIMIZATION_TRICKS.md
$SKILLS_DIR/chankhavu_since_20260601_gain_tricks.md
```

If a doc records an idea as failed and your reasoning says it should work,
re-test it with your own measurements; the failure was often under-exploration.
Record which prior verdicts you re-tested and what you found.

## Same-Task Subagents

If subagent tooling is available, you may spawn subagents, one per focused,
non-overlapping design lane — lanes map naturally onto hypothesis-ledger
families. Subagents must not choose unrelated tasks and must stay on this
`task_id`. Give each the task id, target and budget, bar metrics, the lane
hypothesis, the relevant ledger entries (killed scopes), validation commands, a
separate scratch workspace such as `/tmp/neurogolf_subagents/$TASK/$LANE`, and
required report fields: candidate paths, memory, params, score, validation
status, accepted and rejected ideas, and reusable evidence. The parent merges
results, updates the ledger, and validates exact artifacts.

## Validation

For every candidate, validate the exact builder and ONNX:

```bash
python "$INSPECT_ONNX_SKILL_DIR/inspect_onnx.py" /abs/path/taskNNN.onnx --task-id "$TASK" --include-inits
python "$EVALUATE_SKILL_DIR/scripts/evaluate.py" --input /abs/path/taskNNN.onnx --tasks "$TASK" --verbose
```

A candidate is passing when `evaluate` reports `status=ok`. Optionally add
`--new-samples N --seed S` for an extra robustness check; treat fresh-sample
failures as a debugging hint, not a hard reject. Treat metric issues, score
`0`, score `>25`, NaN, missing memory/params, wrong known examples, or output
contract failure as debugging signals — repair and re-validate.

When both a Python builder and an ONNX file exist, confirm the builder
regenerates the exact ONNX you measured before treating the result as the
candidate's score.

## Honest Turn Endings

Every pause or progress report states: best `status=ok` score so far, target,
remaining gap, budget vs current bar `m+p`, ledger size, and the next family.
Never claim completion before a candidate reaches `status=ok` at or above the
target. "The goal is still active" is the correct ending for unfinished work.

## File Discipline

- Put experiments under `/tmp/neurogolf_single_task/$TASK` or another fresh
  task workspace; keep the hypothesis ledger in `$OUT/notes.md`.
- Do not read the semantic cache or reference files from builders.
- Do not modify unrelated tasks.
- **Name every emitted candidate with its MEASURED memory and params as a suffix** —
  the same suffix on both the ONNX and its Python builder:
  `taskNNN_m{memory}_p{params}.onnx` and `taskNNN_m{memory}_p{params}.py`
  (`{memory}`/`{params}` = the exact values from `evaluate`, not estimates). Emit both
  files for every candidate you keep.

## Progress Reports

Include current task id, target, best `status=ok` score and gap, budget vs
current bar `m+p`, candidates that beat the bar with deltas, hypothesis ledger
size, the cell-dependence analysis summary, and the next planned family.

## Rules

The final graph output must be the complete dense `[1, 10, 30, 30]` tensor.

Do not use ONNX sparse tensors, sparse initializers, or sparse `Constant`
attributes as a memory/params trick. Treat sparse encodings as invalid for
NeuroGolf submissions; use ordinary dense ONNX tensors and dense graph values.

Conv bias inputs are a known local/API/Kaggle stability trap when malformed.
For any `Conv(X, W, B)`, `B` must be a dense 1-D tensor with
`len(B) == W.shape[0]`. Short, scalar, non-1D, missing, or dynamically produced
Conv bias tensors can produce zip-order-sensitive or local/Kaggle score
mismatches, including apparent task score `0`. Prefer two-input `Conv(X, W)`
for new rewrites because bias values count toward params, but do not remove a
nonzero bias mechanically; it may be required for correctness. If stabilizing an
existing malformed champion without a semantic redesign, pad missing bias
entries with explicit zeroes, then rerun checker, strict shape inference,
`inspect-onnx`, and local eval. Expect params to increase and score to drop
slightly.

Scores should satisfy `0 < score <= 25`. Treat score `0`, score `>25`, NaN,
missing memory/params, metric issues, replay/correctness failure, wrong output
shape, sparse tensor usage, or API/local mismatch as debugging signals. Inspect
evaluator output, mismatch samples, graph contract, metric contributors, and
API/local parity; repair and revalidate before submitting or retrying.
